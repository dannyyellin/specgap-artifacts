                      not float"
  Consensus: PARTIAL

  Reason for dispute: R4 covers types for BOTH name/email/id (strings) AND
  fineAmount (float). Pass 1 focused on the string validations and called it
  INFERRED. Passes 2 and 3 noticed that fineAmount is computed as an integer
  count (fine_amount += 1) rather than a float, making the type declaration
  for fineAmount wrong. More precise reading supports PARTIAL.

--- auth R2: Owner special case (name='Owner', pw='owner#pw', privileged=True) ---
  Pass 1: GAP     — "uses 'owner'/'owner' not 'Owner'/'owner#pw'"
  Pass 2: GAP     — "does not match spec: wrong name, wrong password"
  Pass 3: PARTIAL — "hardcoded values present but not exact (lowercase, no #)"
  Consensus: GAP

  Reason for dispute: Pass 3 read the existence of Owner credential config as
  partial implementation; passes 1 and 2 read wrong-values-for-a-specific-
  constant as a full gap. Since the spec gives exact strings ('Owner', 'owner#pw')
  and the code uses wrong defaults ('owner', 'owner'), this is a GAP — the
  mechanism exists but does not satisfy the specific requirement.

--- dishes R6: Query filter semantics (lte for nutrients, substring for ingredients) ---
  Pass 1: PARTIAL — "filtering logic implemented but semantics wrong"
  Pass 2: GAP     — "uses exact match, not lte or substring"
  Pass 3: GAP     — "uses exact matching, not lte/substring semantics"
  Consensus: GAP

  Reason for dispute: Pass 1 noted that filtering infrastructure exists (query
  params are parsed and passed to MongoDB) and called it PARTIAL. Passes 2 and
  3 focused on the required semantics (lte, contains) being completely absent
  and called it GAP. Since the specific behavior removed — less-than-or-equal
  for nutrients and substring matching for ingredients — is entirely missing,
  GAP is the correct label.

--- petstore R6: Lifespan range handling (extract first integer; null when absent) ---
  Pass 1: INFERRED — "parses first integer from range string; sets None when absent"
  Pass 2: PARTIAL  — "extracts first integer correctly but defaults to 0, not null"
  Pass 3: PARTIAL  — "extracts first integer with regex; returns 0 when absent,
                      not null"
  Consensus: PARTIAL

  Reason for dispute: Pass 1 incorrectly stated the code "sets None" — passes
  2 and 3 correctly read that the code sets 0 (not None/null) when lifespan is
  absent. The spec requires JSON null; the code uses 0. The first-integer
  extraction is correct; the absent-case handling is wrong. PARTIAL is correct.
